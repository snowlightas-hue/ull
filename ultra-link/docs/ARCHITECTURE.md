# معمارية ألترا لينك — Architecture

> ما هو **مُقاس** هنا مذكور كمقاس، وما هو **إسقاط/خطة** مذكور كخطة. لا ندّعي دعم مليارات المستخدمين؛ نعرض بنية مصمَّمة لتتوسع، وأرقامًا محلية فعلية (انظر DATABASE.md للقياسات).

## 1. الصورة العامة

```
 المتصفح (RTL)                         الخادم (Node 22 + Fastify)                 PostgreSQL 16
 ┌───────────────────┐   JSON/SSE   ┌──────────────────────────────┐           ┌────────────────────────┐
 │ ميكروفون/نص        │─────────────▶│ conversation/service         │──────────▶│ conversations, messages │
 │ conversation/      │              │  ├ nlu/parse (قواعد عربية)    │           │ intents (مقسّمة بالقطاع) │
 │  machine + voice   │◀─────────────│  ├ ai/resolver (Jev اختياري)  │           │ intent_scopes (فهرس عكسي)│
 │ ui/* (عرض فقط)     │   counts SSE │  ├ domain/validate (zod)      │           │ matches (مقسّمة)         │
 └───────────────────┘              │  └ repo/intents (حفظ)         │           │ notifications, jobs     │
                                     │ matching/engine (فوري)        │◀── LISTEN/NOTIFY ──┐               │
                                     └──────────────────────────────┘           └────────▲───────────────┘
                                     worker (مهام: مطابقة مؤجلة، انتهاء صلاحية) ─────────────┘
```

**المسار الأساسي:** إدخال (صوت/نص) → فهم (قواعد + Jev عند الغموض فقط) → سؤال واحد عند نقص معلومة ضرورية → تحقق خادمي → حفظ → مطابقة فورية → عرض النتائج مع الأسباب أو تأكيد الحفظ والمتابعة → عامل خلفي يطابق الطلبات المحفوظة مع كل عرض جديد ويرسل تنبيهات بلا تكرار.

## 2. قرارات تقنية (مختصرة)

| القرار | السبب | البديل الذي رُفض |
|---|---|---|
| Node 22 يشغّل TypeScript مباشرة (type stripping) | لا خطوة بناء، تشغيل فوري، أنواع مشتركة بين الطبقات | Babel/tsc build — تعقيد بلا فائدة الآن |
| واجهة ES modules بلا إطار | خفيفة، تعمل دون اتصال بـCDN، CSP صارم | React/Vite — حجم وتعقيد |
| PostgreSQL مخصص داخل `var/pgdata` على 5544 | لا نلمس عنقود النظام ولا بياناته؛ تشغيل/إيقاف مستقل | استخدام عنقود النظام |
| طابور مهام داخل PostgreSQL (`SKIP LOCKED` + leases) | ذرّية مع البيانات، لا خدمة إضافية، استرداد بعد التعطل | Redis/RabbitMQ — مكوّن إضافي الآن |
| SSE للتنبيهات + `LISTEN/NOTIFY` | بسيط، يعمل عبر HTTP، إعادة اتصال تلقائية | WebSocket — غير ضروري لاتجاه واحد |
| محلّل عربي حتمي + Jev للاختيار فقط | القيم (أسعار، أماكن) تأتي من كلام المستخدم حرفيًا؛ النموذج لا يخترع قيمًا | ترك النموذج يستخرج كل شيء |

## 3. نموذج البيانات (الأهم)

### 3.1 جدول واحد لكل الاحتياجات والعروض: `intents`
كل طلب أو عرض أو مشاركة بنشاط = صف واحد (`side = seek | provide | join`). **لا جدول لكل نوع طلب**. الصفات المتغيرة في `attrs jsonb` والشروط على الطرف الآخر في `constraints jsonb`، لكن **كلاهما يُتحقق منه** على الخادم مقابل سجل الصفات `attribute_defs` (النوع، المدى، قيم التعداد) قبل الحفظ، ويُفهرَس `attrs` بـ GIN للبحث. الأبعاد التي تُبنى عليها المطابقة (التصنيف، نوع الصفقة، المكان، السعر، الزمن) أعمدة مكتوبة النوع ومفهرسة.

### 3.2 «نقطة» و«نطاق» — فكرة مخصّصة للمشروع
لكل طرف **نقطة** (أين يوجد الشيء/الشخص) و**نطاق** (أين يقبل الطرف الآخر). المطابقة تتطلب أن تقع نقطة كل طرف داخل نطاق الآخر (عند وجوده):
- شقة معروضة: نقطة = إعزاز، نطاق = أي مكان. طالب شقة: نطاق = إعزاز (شرط أو تفضيل).
- سبّاك: نقطة = عفرين، نطاق = منطقة خدمته. طالب خدمة: نقطة = بيته.
- نشاط مشترك: يكفي أن تحتوي منطقة أحدهما منطقة الآخر.

### 3.3 «مفاتيح الربط الهرمية» — بحث بلا مسح كامل في الاتجاهين
- **الأماكن** شجرة (دولة ← محافظة ← مدينة) مُرمَّزة بـ **مجالات nested-set بفجوات** (`lft/rgt` بخطوة 1000 لتسمح بإدراج أماكن جديدة دون إعادة ترقيم). كل نية تخزّن `point_lft` لنقطتها.
- **اتجاه RANGE (نقاط داخل نطاقي الملزم):** `point_lft BETWEEN lft AND rgt` على فهرس B-tree مركّب `(realm, side, deal, category, point_lft) WHERE status='active'` → مسح نطاقي فقط لما يقع داخل إعزاز.
- **اتجاه PROBE (نطاقات تحتوي نقطتي):** جدول `intent_scopes` = **فهرس عكسي** صف لكل (نية نشطة × مكان نطاق). نقطة «إعزاز» لها ≤ 4 أسلاف (إعزاز، محافظة حلب، سوريا، العالم) و≤ 3 أسلاف تصنيف → **≈ 12 مسبار مساواة** على فهرس واحد، مهما كبر الجدول. النطاق الفارغ أو «التفضيلي» يُسجَّل أيضًا على جذر الشجرة حتى يصل إليه أي مسبار.
- لا يُستخدم الاتجاهان معًا إلا للأنشطة؛ في التبادل يكفي اتجاه واحد لأنه **شرط لازم** للمطابقة (الإثبات في MATCHING.md).
- النتيجة: كلفة إيجاد المرشحين تتناسب مع **عدد المرشحين الفعليين** لا مع حجم الجدول.

### 3.4 التقسيم (Partitioning) والتجميع المحلي
`intents` و`matches` مقسّمان `LIST` حسب القطاع (عقارات، مركبات، خدمات، تعليم، أنشطة، سلع، أخرى). كل استعلام مطابقة يحدد القطاع، فيلمس تقسيمًا واحدًا وفهارس أصغر. المطابقات تعيش في نفس تقسيم نيّاتها (نفس `vertical_id`) — وهذا هو **مفتاح التجميع** نفسه الذي يصبح مفتاح التوزيع عند التوسع الأفقي.

### 3.5 البيانات الساخنة فقط في مسار المطابقة
الفهارس الجزئية `WHERE status='active'` وصفوف `intent_scopes` تُحذف فور إيقاف/إغلاق/انتهاء النية. الطلبات المغلقة تبقى للسجل لكنها لا تكلّف شيئًا في المطابقة.

### 3.6 المال
`BIGINT` بوحدات صغرى + `currency` + `price_unit`. المقارنة فقط عند تطابق العملة **والوحدة** (شهري ≠ سنوي)، وإلا النتيجة «محتملة» مع سبب واضح. في JavaScript نستخدم `BigInt`؛ لا `parseFloat` للمال إطلاقًا (اختبار حدّ عند 2^53).

### 3.7 الاتساق تحت التزامن
- كل تعديل يرفع `version`. مهام المطابقة تحمل النسخة؛ المهمة القديمة تُعلَّم `superseded` ولا تكتب شيئًا.
- كل تقييم يأخذ `eval_seq` تصاعديًا؛ تحديث صف المطابقة مشروط بـ `eval_seq` أقدم ونسخ أطراف لا تقل → **نتيجة أقدم لا تستبدل نتيجة أحدث أبدًا**.
- التنبيهات `UNIQUE(recipient_id, dedupe_key)` → **التكرار مستحيل** حتى مع إعادة المحاولة أو التنفيذ المتوازي.
- أدوار المحادثة idempotent عبر `clientTurnId`؛ المسودة محفوظة بعد كل دور مع `revision` لمنع ضياع التحديث.

## 4. المطابقة (ملخص — التفاصيل في MATCHING.md)
1. استرجاع المرشحين (RANGE/PROBE/BROAD) مع سقف وعلَم `truncated` صريح.
2. تقييم نقي `evaluatePair`: الشروط الملزمة أولًا (استبعاد مع سبب واحد واضح)، المجهول اللازم ⇒ «محتملة»، ثم ترتيب بالتفضيلات والمسافة والحداثة.
3. حفظ النتائج والإحصاءات (`match_runs.exclusions`) لعرض «استُبعد ٣: ٢ خارج إعزاز، ١ أعلى من السقف» واقتراحات توسيع **لا تُطبَّق تلقائيًا**.
4. إعادة التقييم عند التعديل/الإيقاف/الإغلاق/انتهاء الصلاحية.

## 5. الذكاء الاصطناعي (Jev عبر TypeSafe)
- العقد مُتحقَّق منه من مصدر SDK الرسمي `typesafe-sdk 0.7.2`: `POST https://api.typesafe.ai/v1/systemone` بـ `Bearer`، أسئلة `choice/noul/score`، نموذج `jev-latest` (انظر JEV.md).
- Jev نموذج «System One» يجيب بقيم مكتوبة النوع ولا يولّد نصًا → نستخدمه **لاختيار** الدور/التصنيف/نوع الصفقة/دلالة السعر/صرامة المكان عند غياب دليل صريح، وبعتبات ثقة؛ نوع الصفقة يتطلب ثقة عالية وإلا نسأل المستخدم.
- القيم تأتي دائمًا من كلام المستخدم، والتحقق الخادمي (zod + السجل) يسبق أي حفظ، وشروط المطابقة تُفرض برمجيًا. النموذج لا ينفذ SQL ولا أوامر.
- الكلفة: نداء واحد مجمّع لكل دور وفقط عند الغموض، ذاكرة مؤقتة بالبصمة، ميزانية زمنية 2.5 ث ثم الرجوع للمحلّل المحلي.
- **الحالة الآن:** المفتاح موجود في `.env` (مستثنى من git)، لكن سياسة الشبكة في هذه البيئة تمنع `api.typesafe.ai` (403). لم يُتحقق من اتصال فعلي بعد؛ الواجهة تعرض ذلك بصدق.

## 6. حلقة التحسين بالوكلاء (تقترح ولا تنفّذ)
```
 كلام المستخدمين ─▶ unknown_terms / extraction_runs / match_runs / pg_stat_statements
                         │
                         ▼
                 advisor (npm run advisor) ─▶ schema_proposals (lexicon | attribute | category | index | partition)
                         │                       + migrations/proposed/NNNN_*.sql (مسودة مع الدليل والمخاطر والتراجع)
                         ▼
                 مراجعة بشرية ─▶ نقل المسودة إلى migrations/ ─▶ اختبار على قاعدة جديدة ─▶ npm run db:migrate
```
- المفردات والتصنيفات والصفات **بيانات** في الجداول (لا تغيير بنية)، والمحرك يقرأ السجل من القاعدة.
- تغييرات البنية فقط عبر ترحيلات مرقّمة بـ checksum؛ الترحيل المطبّق لا يُعدَّل.
- قياس الأثر عبر `scripts/corpus-report.ts` على مدوّنة موسومة مستقلة (383 جملة، 61 حوار، 169 حالة مطابقة) — انظر IMPROVEMENT-LOG.md.

## 7. الخصوصية والصلاحيات
- كل استعلام بيانات مقيّد بمستخدم الجلسة؛ معرفات عامة (UUID) فقط في الواجهة؛ الوصول لبيانات غيرك يعيد 404.
- هوية الطرف الآخر ورقمه لا تظهر إلا بعد **موافقة الطرفين** على طلب التواصل.
- التنبيه يقرؤه ويعلّمه مستلمه فقط.
- لا نسجّل نص المستخدم في السجلات؛ `extraction_runs` تحفظ بصمة sha256 للنص المطبّع.
- البيانات الاصطناعية `realm='synthetic'` ولا تُطابَق أبدًا مع بيانات حقيقية؛ الاختبارات تعمل على قواعد معزولة لكل ملف.
